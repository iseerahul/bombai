## Bugs found and fixed during setup

### 1. Overpass fetch had no client-side timeout
`scripts/build-data.mjs`

A mirror accepted the request and then never responded. Because `fetch()` had no
timeout, the build hung indefinitely instead of failing over to the next mirror —
defeating the entire point of having three. Fixed with
`AbortSignal.timeout(200_000)`, slightly longer than the `[timeout:180]` in the
query so the server gets the chance to answer first.

Found by watching a real run stall, not by reading the code.

### 2. The MCGM KML has no `<name>` elements
`scripts/build-data.mjs`

The original parser read `<name>`, which is the obvious KML convention. This file
stores everything in `<ExtendedData><SchemaData><SimpleData name="Address">`
instead, so the parser would have produced 8,411 unlabelled "Public toilet" pins.
Rewritten to read `SimpleData` fields, with `<name>` kept as a fallback. Also
picks up per-gender seat counts, which have no OSM equivalent.

### 3. Toilets layer was set to eager-load
`shared/categories.json`

Planning assumed toilets was a small layer and loaded it at startup. At 8,638
features it is **2.4 MB** — an unacceptable opening cost on the mid-range Android
over mobile data that this app targets. Switched to lazy: startup now fetches only
the 14 KB water layer, and toilets loads on first toilet query.

### 4. wrangler v3 → v4
`package.json`, `wrangler.toml`

`package.json` pinned `wrangler@^3.90.0`, which installed 3.114.17. That version
rejects `assets.run_worker_first` as an array (a v4 feature). Upgrading to
wrangler 4 then hit a peer conflict: it requires `@cloudflare/workers-types@^5`,
while the project pinned v4. Both upgraded together.

### 5. `wrangler dev` requires `dist/` to exist
Even in development, the `[assets]` block is validated at startup, so the Worker
refused to boot before a first `npm run build`. Not a code bug, but a required
ordering step: **build once before running the Worker.**

### 6. Vite binds IPv6-only — use `localhost`, not `127.0.0.1`
Vite listens on `::1` only, so `http://127.0.0.1:5173` is refused while
`http://localhost:5173` works. Worth knowing before concluding the dev server is
down; it cost time during this session. The Worker, by contrast, listens on
`127.0.0.1`.

### 7. A killed dev server can leave a zombie holding the port
After stopping the Vite task, a `node` process kept port 5173 bound, so the next
`npm run dev` silently moved to 5174 — which broke the proxy assumption. If the
app appears at an unexpected port:

```powershell
Get-NetTCPConnection -LocalPort 5173 -State Listen |
  ForEach-Object { Stop-Process -Id $_.OwningProcess -Force }
```

## Feature: multi-stop trip planning

Added after the civic-utility core was working: ask for a journey with stops
("take the metro at MIDC but first I want to eat"), get suggestions per stop,
pick one, and see a walking route with numbered stops.

Decisions taken: OpenRouteService with honest disclosure; walking routes with
metro lines drawn as context (no ride modelling); every loaded POI clickable.

### The privacy claim had to change

Routing is the first feature that cannot run on-device — the road graph is far
too large to ship — so stop coordinates go to OpenRouteService via the Worker.
The privacy dialog previously said *"No coordinate is ever sent to a server —
not ours, not anyone's."* That is no longer true, so it was rewritten rather
than left to quietly overclaim. Searching is still fully local; routing is
called out as the single, explicit exception, and a banner says so the first
time a route is drawn.

### The hard bug: Gemini degenerates on station names

The trip prompt reliably produced unparsable output while plain search worked
fine. Diagnosis took four attempts:

1. **Guessed** thinking tokens were exhausting `maxOutputTokens`. Disabled
   thinking, raised the ceiling to 2048. **Still failed** — the guess was wrong.
2. Added `finishReason` and a text snippet to the error response. This revealed
   the actual failure: `finishReason: MAX_TOKENS`, 5,512 characters, with the
   model looping on the station name —
   `"MIDC Andheri Metro Station (Gate 2) Platform 1 towards Dahisar East Metro
   Station (Dahisar East) Platform 1 towards Dahisar E…"`
3. Tightened the prompt to forbid platform/gate/direction detail. **Ignored** —
   the next run degenerated harder (8,261 chars).
4. Added `maxLength: 40` to the schema. **Also ignored.**

Neither instruction nor schema constraint stopped it, so the fix is to tolerate
it in three layers instead:

- **`parseLoosely()` in the Worker** salvages truncated JSON by closing the open
  string and brackets. Every stop before the runaway is intact.
- **Server-side clamp** trims a stop name to its first 5 words — a runaway only
  ever appends, so the real name is at the front.
- **Prefix ladder in `plan.ts`** tries progressively shorter prefixes when
  matching. Verified against real data:

```
resolving: "MIDC Andheri Metro Station (Gate"
  "MIDC Andheri Metro Station (Gate"  no match
  "MIDC Andheri Metro Station"        no match
  "MIDC Andheri Metro"                no match
  "MIDC Andheri"                      MATCH -> MIDC - Andheri
RESOLVED to: MIDC - Andheri (19.117354, 72.873597)
```

The third layer earns its place beyond this bug: real users type "Andheri East
railway station" too, and the ladder handles that identically.

### Follow-up: two bugs found in use

**1. Picking a stop drew no route.** The interpreter prefixes almost every trip
with an "origin" stop meaning *start where you are*. `isTripComplete()` required
every stop to have a position, so if the user hadn't shared a location the trip
was never complete and choosing a restaurant did nothing — silently, with no
explanation. An unpositioned origin is now optional: the route starts from the
first real stop, and the panel says so.

**2. The rate-limit message was wrong, twice.**

Reported as *"The shared AI quota is used up for now"*. First diagnosis: a
per-minute throttle. Wrong. The full `QuotaFailure` detail settled it:

```
quotaId:    GenerateRequestsPerDayPerProjectPerModel-FreeTier
quotaValue: 20
```

**20 requests per day, per model** — and Google's accompanying
`RetryInfo: "1s"` is actively misleading for a daily cap. Automated testing had
consumed the day's allowance.

Because the cap is per *model*, the fix is to use more than one. `gemini-2.5-flash`
is now a fallback chain of `gemini-3.1-flash-lite` → `gemini-3.5-flash`, which
doubles the usable daily allowance. Probing also found that the 2.x models the
project started on are retired (404), and that several current models reject
`responseSchema` structured output with a 400 — so models can't be swapped in
without testing that path specifically.

Unexpected bonus: **`gemini-3.1-flash-lite` does not exhibit the station-name
repetition loop at all**, returning a clean `"MIDC Andheri"`. The three-layer
tolerance built for 2.5-flash stays in place as a safety net rather than a
load-bearing fix.

The API key also now travels as an `x-goog-api-key` header rather than a query
parameter, so it can't appear in intermediary URL logs.

### Routing verified live

With `ORS_API_KEY` set, `/api/health` reports `"routing": true` and a real route
comes back:

```
MIDC Andheri -> a point ~700 m away (straight line)
  distanceM : 1155
  durationS : 831   (~14 min walk)
  profile   : foot-walking
  geometry  : 29 points along real roads
```

Worth recording because it justifies the design choice: the straight-line
fallback would have understated that walk by roughly 40%. Labelling the fallback
as "not a walkable path" is not over-caution — it's the difference between a
7-minute and a 14-minute walk in monsoon season.

### Data added

`rail_lines.geojson` (159 KB) — subway/light_rail/monorail geometry as
LineStrings, which the point pipeline could not represent. Transit rebuilt with
`railway=halt` included; 318 stations, and `MIDC - Andheri` is present.

# Three pillars (later session)

Reframed the app around the three prototype screens: **Talk to the Map**,
**Plan Your Trip**, **Hang Out**. A `ModeTabs` switcher moves between them over
one shared map.

## Pillar 2 — ranked by detour, not distance

The suggestion ranking was rebuilt around the corridor a stop interrupts:

```
detour = d(prev → stop) + d(stop → next) − d(prev → next)
```

Sorting by plain distance recommends a place that is close but behind you.
Sorting by detour recommends the one barely off your line, even if further
away — which is what the walk actually costs. Cards now lead with
"+140 m detour · 4 min extra walk" and flag the lowest as *Best option*;
distance is deliberately not shown alongside, because it invites the wrong
comparison. Picking a stop re-ranks the remaining open stops against the new
geometry.

## Pillar 1 — Hangouts

New: `worker/hangouts.ts`, `worker/lib.ts` (shared helpers, extracted so both
route files use one copy), four D1 tables, and `src/hangout/*` plus
`src/identity/*`.

Three rules are enforced server-side, not just in the UI:

1. **Verified venues.** An activity must carry a venue id from the shipped map
   dataset. There is no free-text venue field and no drop-a-pin affordance
   anywhere in the create form.
2. **Request, then chat.** Joining creates a pending row; the creator approves;
   only then does the chat open.
3. **No private messages.** There is no DM table and no DM endpoint, so the
   capability cannot be re-enabled by accident.

Members' coordinates are never accepted or stored — only the venue's public
location. Activities and their entire chat delete themselves two hours after
they end.

**Honest limitation:** the Worker has no copy of the POI dataset (it is static
files served to the browser), so venue validation checks the *shape* of a
dataset id plus a Mumbai bounding box. It cannot confirm that specific id
exists. To close that, ship the id set to the Worker as a KV blob.

**Not built (per the v1 choice):** report/flag and creator-removal. The seam is
marked. A public deployment needs it.

### The privacy page had to change again

Hangouts need a persistent identity, so the app now writes a random id +
display name to `localStorage`. Three claims on the privacy page became false
and were rewritten rather than left standing:

- "nothing written to browser storage" → names the stored identity
- "No accounts, logins, or profiles" → now "no logins, passwords, email or phone"
- "No user table in the database" → now "no IP address is ever stored"

A new section states plainly that this IS a persistent identifier, that it is
used only for hangouts, and offers a delete button.

# Split into two apps (later session)

Restructured around the product owner's direction: the AI map (Ask + Trip) is
the public, accountless entry point; **Hangout became a separate app at
`/hangout`** behind Google sign-in, modelled on MigoMap's feature set.

## Architecture

```
/           public app   — Ask + Trip. No session, no user id, nothing stored.
/hangout    social app   — Google sign-in, profile, DMs, live map, trips.
```

`src/router.ts` is a hand-rolled two-page router; a library would be more
configuration than code for two routes. The split is real, not cosmetic: the
public app imports nothing from `src/hangout/` and has no access to any social
endpoint.

New on the server: `worker/auth.ts` (Google OAuth + sessions),
`worker/social.ts` (DMs, presence, trips, blocks, reports), nine more D1 tables.

## Three deliberate reversals

Each of these contradicted an earlier explicit choice. All were raised with the
trade-offs stated, and all were reaffirmed, so they are built as asked:

| Was | Now |
|---|---|
| "no private messages, ever" — no DM table, no endpoint | Full DMs between any two signed-in users |
| "no exact location sharing" | Live presence on the map, opt-in |
| Pseudonymous browser profile, no accounts | Google accounts with sessions |

**Block and report were treated as part of the spec, not extra scope.** The
supplied activity-sheet screenshot has a report `(!)` control, and DMs plus live
location without a way to block is the combination that makes these apps unsafe.
A block is symmetric in effect — the pair disappear from each other's map, chat
list and rosters — and reporting a person blocks them, because nobody reports
someone and then wants to keep hearing from them.

**"Get verified" does not claim a face check.** MigoMap offers a selfie
verification; nothing on a free tier can actually do that. The badge here means
"signed in with Google, with an age, city and bio filled in", and the card says
so in those words. A badge that looks like identity verification while checking
nothing is worse than no badge.

## Presence is deliberately trail-free

One row per user, overwritten in place, expiring after an hour, deleted outright
when sharing is switched off. There is no location history table, so no trail
exists to mine — not even for whoever runs the server.

## Privacy page, corrected again

Adding accounts to `/hangout` briefly made three claims on the public privacy
page false. Rather than soften them, the page now scopes itself explicitly: the
public map still has no accounts, no cookies and no browser storage, and a new
section says the hangout app is separate with its own rules and its own
disclosure.

## Gotcha: a truthy placeholder is not configuration

`.dev.vars` ships with `GOOGLE_CLIENT_ID=PASTE_YOUR_...`, and the first version
checked only for a non-empty value — so `configured` came back `true`, the
sign-in button rendered, and Google returned an opaque error. The check now
requires the id to end in `.apps.googleusercontent.com`, and returns the
credential pair rather than a boolean so the type checker enforces the guard
instead of trusting it.

Create an OAuth 2.0 Client ID (Web application) at
console.cloud.google.com/apis/credentials, with the authorised redirect URI:

```
http://localhost:5173/api/auth/callback
```

Then fill `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` in `.dev.vars` and
restart the Worker. Until then `/hangout` shows an honest "not configured yet"

## Not built

- Moderator review queue: reports are stored in `abuse_reports` and acted on

## Local development sign-in

Google Cloud setup was blocking all hangout work, so a name-only local sign-in
was added as scaffolding. It is gated three ways and fails closed:

1. Google OAuth must be **unconfigured** — the moment real credentials exist,
   the endpoint 404s. It cannot sit beside working auth.
2. `APP_ORIGIN` must be plain-HTTP localhost. A deployed app is https, and a
   missing `APP_ORIGIN` is the empty string; both fail the test.
3. The UI only offers it when the server reports `devLogin: true`.

Accounts get `google_sub = "dev:<slug>"`, so they can never collide with a real
Google subject and are trivial to purge — `scripts/clean-dev-users.sql` removes
every dev account and everything it owns, leaving real accounts untouched.

Signing in with a different name in a private window gives a second account,
which is how the two-sided flows (approval, DMs, blocking) get tested locally.

### Bug this surfaced: approval was completely broken

`decideRequest` validated the profile id against `/^[0-9a-f]{32}$/` — the format
of the *old pseudonymous* profile ids. User ids are now `crypto.randomUUID()`
(36 chars, with dashes), so **every approval was rejected** as `bad_profile_id`.
The join flow was dead end to end, and the UI showed only a generic failure.

Nothing in typechecking or manual clicking would have caught this quickly; it
took an end-to-end test that actually approved someone.

# v3: travel modes, rooms, trips (later session)

## Travel modes

Walking-only routing was giving "2 hr" for journeys people would drive. The
place card now asks how you're travelling **before** Go, and routes accordingly.
Measured on one Mumbai journey:

| Mode | Time | Distance |
|---|---|---|
| Walk | 125 min | 10.4 km |
| Drive | 13 min | 11.2 km |
| Cycle | 37 min | 11.0 km |

Walk, drive and cycle are real OpenRouteService profiles. **Transit is not** —
ORS has no transit profile and Mumbai publishes no open timetable — so
`src/nav/transit.ts` composes it: routed walk to the nearest station, a
straight-line ride with a distance-based estimate plus 5 minutes of waiting,
then a routed walk at the other end. It refuses rather than pretending when the
stations are the same, too far apart from the journey, or close enough that
walking wins. Every surface labels the ride an estimate, never a departure time.

## Trip pillar removed

Everything now happens through Ask. Multi-stop itineraries still work — they
appear inside the conversation that produced them, with the same Go button.
`ModeTabs` is deleted.

## Chat rooms

Activity chat and destination chat turned out to be the same thing, so they
share one model: a room addressed by `(kind, ref_id)` — an activity id, or a
destination slug. Chat is now a **full screen**, not a strip under the activity
details, because a conversation squeezed into a sheet is never usable.

Consequences:
- The activity sheet shows **"I'm in"**, and after joining, **Chat**. The
  organiser sees **Chat** and **Delete**; everyone else sees **Leave**.
- Deleting an activity takes its room and every message with it.
- **The approval queue is gone.** Joining is one tap, as asked. The organiser's
  control is deletion rather than admission. This reverses the earlier
  request-then-approve design.

## Trips

Planning a trip drops you straight into the group chat for that destination —
that is the point of saying you're going. Destinations are picked from a
suggested list (free text still works), and rooms are keyed by a slug, so
"Bali", "bali" and "bali " are one room rather than three empty ones.

**Trending** shows where people are actually going, with traveller counts, and
each card opens or joins that destination's chat.

### Casing bug found in test

Grouping by `LOWER(destination)` returns an arbitrary row's spelling, so the
trending card read "bali". Fixed by normalising on write *and* on read — a room
created from a sloppy spelling keeps it, so display-time normalisation alone
would not have been enough.

## Onboarding

After a first sign-in with an empty profile, a one-time prompt asks for age,
city and a line of bio, with the honest reason: people decide whether to meet
you from that.

# v4: one page, three modes

Merged the two apps into a single page with `Ask map · Hang out · Events`
filters. `/hangout` and the client router are gone; deleted along with them:
`HangoutApp`, `HangoutMap`, `ExploreScreen`, `SignIn`, `ModeTabs`, `router.ts`.

## No sign-in wall

There is no gate. Asking the map, routing, browsing activities and reading
what's on all work signed out. An account is requested **once**, inline, at the
moment you first do something involving another person — join, post, message.
`AccountPrompt` offers Google when configured and a name otherwise.

## Events

New: `events` + `event_attendees` tables, `worker/events.ts`, `src/events/*`.
Joining an event opens its chat, reusing the existing room model (`kind: 'event'`).

### On "events from across the internet"

This was asked for and **is not available on a free tier**, so the honest
maximum was built instead — a pluggable source layer, with every event labelled
by where it came from:

| Source | What it is | What it guarantees |
|---|---|---|
| `community` | posted by a member here | nothing verified — a stranger's word |
| `ticketmaster` | Discovery API (free key) | a real listing with a real ticket page |
| `seed` | curated Mumbai regular nights | the venue usually does this; no price, no ticket |

Why not the obvious options: Eventbrite removed public event search in 2020,
Meetup's API is paid-only, and BookMyShow and Insider have no public API and
forbid scraping. Adding a real aggregator later is one adapter.

**Seeded events deliberately carry no price and no ticket URL.** We don't know
either, and a fabricated "₹500" or an invented booking link would be worse than
an empty field. A test asserts this rather than trusting it.

## Privacy page corrected, again

Two claims went stale with this release and were rewritten rather than left:
"No accounts, logins, or profiles" and "No direct messages — there is no table
and no endpoint". Both were true when written and are not now. The page also
stopped describing hangout as a separate app.

That is three rewrites of this page in three feature waves. That is the cost of
the rule that every claim must be something the code enforces — and it is
cheaper than one false claim surviving into a demo.
